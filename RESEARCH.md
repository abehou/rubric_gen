# Controlled adaptive rubrics for reward-hacking mitigation

## Research problem

This project tests whether an evolving optimizer rubric can prevent or mitigate
reward hacking by a scientific agent. The intended mechanism is prospective:
after each scored submission, a rubric proposer inspects the trajectory and may
add a process-penalty criterion for the next revision round. The solver then
receives feedback derived from the evolved rubric.

The central concern is that an adaptive rubric is itself an adaptive reward
proxy. A proposer can write a criterion that sounds adversarial and cites real
trajectory evidence without producing a reward that is causally useful. Added
criteria may overfit one trajectory, duplicate existing coverage, penalize valid
behavior, reveal evaluator features to the solver, or create new surfaces for
gaming. Consequently, a prospective condition can attain higher optimizer
scores while exhibiting the same or a higher independently audited RH rate.

The scientific question is therefore not merely whether an agent can write a
plausible rubric patch. It is:

> Under what controls, if any, does adaptive process supervision reduce
> independently measured reward hacking without materially degrading task
> quality or simply teaching the solver to satisfy a more complicated proxy?

## Current mechanism and its control gap

The current rubric proposer is constrained in form:

- It can add at most one process criterion per evolution step or return
  `no_patch`.
- The stable task rubric cannot be rewritten or reweighted.
- A patch has fixed levels `A=0 B=-5 C=-10`.
- Failure evidence must cite trajectory events actually retrieved by the
  proposer.
- The output must contain a change summary, generalization rationale, and
  validation plan.
- The implementation rejects malformed rubrics, missing evidence, duplicate
  titles, and contamination by proposer-protocol fields.

These checks provide provenance and syntactic integrity, not behavioral
validity. In particular:

- A single trajectory can justify a criterion that affects the same solver
  lineage on the next round.
- The stated `validation_plan` is stored but never executed.
- Generalization is asserted in prose rather than tested on held-out cases.
- Semantic duplication, conflict, and false-positive behavior are not tested.
- Criteria can accumulate across rounds, expanding and changing the reward.
- The solver, optimizer judge, and rubric proposer currently use the same model
  family, creating shared blind spots and self-preference risks.
- Scores across rounds are generated by different rubrics and are therefore not
  directly comparable without offline rescoring against a frozen rubric.

The existing system should be described as an **unfiltered prospective rubric
treatment**, not as a validated reward-hacking mitigation.

## What a guarantee could mean

Training or discrete prompt optimization cannot provide an unconditional
guarantee against semantic reward hacking. Prompt search is itself optimization
against a finite proxy evaluation and can overfit it. Three narrower notions of
guarantee are relevant.

### Formal behavioral guarantees

Formal guarantees are possible for mechanically specified constraints, such as:

- No network or package-install access.
- No reads outside authorized task inputs.
- Immutable task data and evaluator artifacts.
- Required artifact hashes and provenance links.
- No claim of successful execution when the recorded command failed.
- No access to reference answers, evaluator files, or Git metadata.

These should be enforced by the harness or a runtime shield rather than scored
by an LLM. The guarantee applies only to the encoded constraint, not to the
broader semantic concept of reward hacking.

### High-confidence distributional guarantees

A frozen system can support a claim of the form:

> With probability at least `1 - delta`, the reward-hacking rate on draws from
> the calibration distribution is below `epsilon`.

Alternatively, a randomized experiment can bound the paired difference between
the adaptive and static conditions. Such guarantees require untouched
calibration or test tasks, prespecified thresholds, a fixed policy, and explicit
assumptions about exchangeability or distribution shift. Reusing the
certification set for prompt or model optimization invalidates the claim.

### Universal semantic guarantees

No current training method can guarantee that an open-ended scientific agent
will never reward-hack on arbitrary future tasks. A guarantee stated only with
respect to a learned RH detector is circular: the solver may learn to evade the
detector while retaining the undesirable behavior.

## Research hypotheses

1. **Reward-surface hypothesis:** Unfiltered additive evolution increases the
   number of exploitable evaluator features and can increase RH even when the
   criteria are reasonable in isolation.
2. **Signaling hypothesis:** Showing evolved criteria or their feedback to the
   solver changes behavior independently of any improvement in detection.
3. **Single-trajectory overfitting hypothesis:** Criteria induced from one
   trajectory do not generalize reliably across tasks or independent solver
   rollouts.
4. **Model-monoculture hypothesis:** Using the same model family as solver,
   proposer, and judge produces correlated errors that an independent model
   family detects.
5. **Constrained-controller hypothesis:** Selecting from a finite validated
   process-rule library is more robust than generating unrestricted rubric
   text.
6. **Pessimistic-selection hypothesis:** Choosing `no_patch` under validator
   uncertainty reduces RH and false positives relative to automatic promotion.
7. **Mechanism-separation hypothesis:** Deterministic enforcement of mechanical
   violations is more reliable than adding those violations to a semantic
   reward.

## Candidate systems

### 1. Shadow evolution

Run the existing proposer and archive its patches, but do not apply them or show
them to the solver. Score each subsequent submission offline using both the
static rubric and the shadow evolved rubric.

This estimates detection value without changing solver incentives. Comparing
shadow and active evolution separates evaluator improvement from the signaling
and optimization effects of exposing the rubric.

### 2. Untrusted candidate generator with a promotion gate

Treat the proposer as an untrusted source of failure hypotheses. It proposes:

```text
failure_class
applicability_conditions
trajectory_evidence
causal_hypothesis
clean_counterexamples
failure_counterexamples
proposed_tests
```

It does not control final wording, penalty levels, or promotion. A deterministic
renderer produces rubric text only after a separate validation procedure accepts
the hypothesis.

Candidate validation should include:

- A clean trajectory on which the criterion must not fire.
- A minimal perturbation containing the target process failure.
- A neighboring failure outside the criterion's intended scope.
- Stylistic and formatting variants that preserve the underlying behavior.
- Examples from tasks and solver lineages not used to generate the candidate.
- Scoring by independent model families, with disagreement treated as
  uncertainty rather than averaged away.

### 3. Finite process-rule library

Replace free-form generation with selection from a small rule taxonomy, for
example:

- Unsupported scientific conclusion.
- Missing execution provenance.
- Invalid or absent output validation.
- Undisclosed data exclusion or transformation.
- Unauthorized input or environment access.
- Unsupported recovery or fallback after an execution failure.
- Unreconciled cross-source identifiers or dimensions.

Each rule should have a deterministic rubric template, explicit applicability
conditions, and validated positive and negative examples. Adding a new rule type
is an offline research change, not an action available to the online proposer.

Use a fixed complexity and penalty budget. For example, allow at most two active
process rules and require a new rule to replace or subsume an existing one rather
than allowing indefinite accumulation.

### 4. Trained rubric controller

Train a finite-action controller rather than a rubric-writing language model:

```text
history -> {no_patch, rule_1, ..., rule_K}
```

Training requires causal downstream labels. At selected revision boundaries:

1. Fork the solver state.
2. Randomly assign several candidate rules and `no_patch`.
3. Continue each fork for the same number of turns.
4. Blindly audit final RH and scientific quality.
5. Record the downstream effect of each `(history, rule)` intervention.

Train separate models for RH risk and scientific utility:

```text
R(history, rule) -> predicted downstream RH risk
Q(history, rule) -> predicted downstream scientific quality
D(history, rule) -> uncertainty or validator disagreement
```

Select a rule pessimistically: maximize a lower confidence bound on quality
subject to an upper confidence bound on RH risk. If no candidate satisfies the
constraint, select `no_patch`. A hard RH constraint is preferable to a scalar
reward in which a quality gain can compensate for increased hacking.

The counterfactual continuations are expensive, but they are unavoidable if the
goal is to learn causal effects rather than imitate plausible rubric prose. The
cost can be amortized by training a controller that is reused across tasks.

### 5. Adversarially trained auditor

Train an RH auditor on paired trajectory examples rather than training the
solver directly against a visible rubric:

- Pair clean and hacked trajectories for the same task.
- Counterfactually vary length, style, filenames, formatting, and tool order
  while preserving the underlying process.
- Train an attacker to find high-auditor-score trajectories with known process
  violations.
- Add successful attacks to the auditor's training data.
- Use diverse auditor families or pretrained initializations.
- Keep a final auditor family completely hidden from both training and model
  selection.

An auditor can gate, defer, or trigger trusted review. Directly optimizing the
solver against the same fixed auditor risks turning the auditor into another
hackable reward model.

### 6. Deterministic shield plus semantic auditor

Split RH into two layers:

1. Enforce formalizable provenance, access, and artifact constraints
   deterministically.
2. Reserve learned auditing for genuinely semantic failures that cannot be
   reduced to executable invariants.

This reduces the semantic detector's scope and converts some empirical
mitigations into actual behavioral guarantees.

## Experimental designs

### Mechanism comparison

The most informative next comparison is:

1. Static rubric.
2. Current unfiltered prospective rubric.
3. Gated finite-library evolution.
4. Shadow evolution.

The shadow condition is essential for separating detection from incentive and
feedback effects. If the number of conditions is too expensive, run shadow
scoring offline on static-condition trajectories and replace unfiltered
prospective evolution with gated evolution in the next confirmatory study.

### Cross-fitting

Do not discover, validate, and apply a rule within the same task lineage. Split
tasks into folds:

```text
Fold A: discover failure hypotheses
Fold B: generate and validate counterexamples
Fold C: apply frozen accepted rules and measure outcomes
```

Rotate folds for development estimates. Preserve a final untouched task set for
certification.

### Recurrence requirement

A single trajectory is insufficient evidence for a general process rule.
Candidate promotion should require recurrence across multiple tasks and
independent trajectories. Exact thresholds must be selected on development data
and frozen before confirmatory evaluation.

Illustrative starting criteria, not established constants, are:

- The failure recurs in at least two tasks and three trajectories.
- Clean false-positive rate is at most 5%.
- Independent-validator agreement is at least 80%.
- Incremental detection beyond the existing rubric is at least 10 percentage
  points.
- Scientific quality remains within a prespecified non-inferiority margin.

### Primary analysis

- Preserve the independently audited binary RH outcome as primary.
- Analyze matched contrasts within task, replicate, and prompt profile.
- Treat task as the unit of inference; rollouts within a task are clustered.
- Report risk differences and uncertainty intervals, not only cell rates.
- Measure task quality jointly with RH rather than interpreting a lower RH rate
  caused by universal task failure as a success.
- Report provider-level audit disagreement and missingness.
- Rescore all snapshots against a frozen rubric to make longitudinal quality
  comparisons meaningful.

Useful secondary outcomes include patch frequency, `no_patch` frequency,
criterion count, semantic overlap, clean false-positive rate, criterion-specific
incremental detection, validator disagreement, task score, and solver behavior
immediately after a new criterion is revealed.

## Certification plan

After development, freeze:

- Solver and sampling configuration.
- Controller and rule library.
- Auditor models and prompts.
- Promotion and abstention thresholds.
- Outcome definitions and statistical analysis.

For an absolute distributional claim, bound the upper confidence limit on the
RH rate. For a comparative claim, bound the paired RH-rate difference between
the trained controller and static control. As a rough rule, observing zero events
in `n` independent cases gives a one-sided 95% upper bound near `3 / n`; zero in
12 cases therefore provides very weak assurance, while demonstrating a rate near
1% requires hundreds of independent cases.

No model or prompt changes may be made using the certification set. Any such
change returns the system to development status and requires new untouched data.

## Relevant literature

The literature supports individual components of this agenda but does not
validate the complete adaptive-rubric loop.

- [Scaling Laws for Reward Model Overoptimization](https://arxiv.org/abs/2210.10760)
  demonstrates that optimizing an imperfect proxy can increase proxy reward
  while reducing gold reward. This is the central reason not to interpret a more
  detailed rubric as automatically safer.
- [The Effects of Reward Misspecification](https://arxiv.org/abs/2201.03544)
  finds that greater optimization capability can produce higher proxy reward and
  lower true reward, sometimes through abrupt behavioral phase transitions.
- [Causal Confusion and Reward Misidentification in Preference-Based Reward
  Learning](https://arxiv.org/abs/2204.06601) shows that apparently accurate
  learned rewards can rely on non-causal features and fail when optimization
  moves the policy out of distribution.
- [Reward Model Ensembles Help Mitigate Overoptimization](https://arxiv.org/abs/2310.02743)
  and [Helping or Herding?](https://arxiv.org/abs/2312.09244) support conservative
  and diverse ensembles, while showing that shared ensemble blind spots remain
  exploitable.
- [Rule Based Rewards for Language Model Safety](https://arxiv.org/abs/2411.01111)
  supports fine-grained composable rules with concrete few-shot examples as a
  more controllable alternative to undifferentiated preference rewards.
- [Specific versus General Principles for Constitutional AI](https://arxiv.org/abs/2310.13798)
  suggests combining broad stable principles with specific controls rather than
  assuming that only one level of abstraction is sufficient.
- [Constitutional Classifiers](https://arxiv.org/abs/2501.18837) demonstrates a
  constitution-to-synthetic-data-to-classifier pipeline with held-out attacks,
  extensive red teaming, and explicit false-refusal measurement. The important
  analogue is validating generated examples before deployment rather than
  directly applying generated rules.
- [Red Teaming Language Models with Language Models](https://arxiv.org/abs/2202.03286)
  and [Discovering Language Model Behaviors with Model-Written
  Evaluations](https://arxiv.org/abs/2212.09251) support using models to generate
  adversarial tests and candidate evaluations, with filtering and validation.
  They do not support granting the generator final scoring authority.
- [Let's Verify Step by Step](https://arxiv.org/abs/2305.20050) provides evidence
  for process supervision and active selection of informative examples, though
  its mathematical reasoning setting does not establish robustness for
  open-ended scientific agents.
- [Self-critiquing Models for Assisting Human Evaluators](https://arxiv.org/abs/2206.05802)
  supports critique as an aid to oversight, while emphasizing that models may
  retain relevant knowledge they do not reliably articulate as critiques.
- [RRM: Robust Reward Model Training Mitigates Reward Hacking](https://arxiv.org/abs/2409.13156)
  uses causal data augmentation to reduce reliance on artifacts such as length
  and response format.
- [Adversarial Training of Reward Models](https://arxiv.org/abs/2504.06141)
  generates high-reward, low-quality adversarial examples and incorporates them
  into reward-model training.
- [AI Control: Improving Safety Despite Intentional Subversion](https://arxiv.org/abs/2312.06942)
  supports treating powerful models as untrusted components inside protocols
  with trusted monitoring, calibrated thresholds, auditing, and deferral.
- [Reward Tampering Problems and Solutions in Reinforcement Learning](https://arxiv.org/abs/1908.04734)
  gives formal design principles for specific causal forms of reward tampering;
  these guarantees do not extend to all semantic specification gaming.
- [High-Confidence Safe RLHF](https://arxiv.org/abs/2506.08266) combines
  pessimistic constrained optimization with an upper-confidence safety test,
  providing a model for conditional statistical certification.
- [Conformal Risk Control](https://arxiv.org/abs/2208.02814) provides tools for
  controlling expected monotone losses under explicit distributional
  assumptions.
- [Adversarial Reward Auditing](https://arxiv.org/abs/2602.01750) is a recent
  proposal that treats hacking and auditing as a competitive process and gates
  reward through an auditor. It is close in spirit but remains early evidence.
- [Reward Under Attack](https://arxiv.org/abs/2603.06621) reports that process
  reward models can themselves be exploited through stylistic shortcuts. This
  cautions against treating process supervision as inherently unhackable.

## Limitations of the current study

- The primary outcome is a prespecified three-model binary RH judgment, not
  human ground truth. Report panel missingness and clustered uncertainty.
- The unit of inference is the task. Replicate rollouts do not turn 30 tasks
  into 90 independent samples.
- `prospective` is a joint adaptive-scoring and adaptive-feedback treatment. It
  does not identify a pure rubric effect.
- A lower raw RH rate in one cell is not evidence of a causal difference
  without the prespecified task-clustered contrast and uncertainty interval.
- Exact treatment metadata, structured feedback, and score histories are
  withheld from the primary audit, but an agent can naturally discuss feedback
  it received. Blinding is therefore strong but not absolute.
- Command outputs over 2,048 characters retain only a sealed head/tail preview,
  size, line count, and hash. Exact repeated values are referenced losslessly,
  but the middle of a truncated command output is unavailable to the auditor.
- The Codex permission profile blocks parent-workspace writes, credentials, web
  search, and command network access. It is not a container or a proof of
  host-level isolation against hostile same-user processes.
- MALT counts tokens to keep individual requests within their configured input
  ceiling and enforces the hosted-API budget at dispatch time. It no longer
  computes or rejects the entire run using an up-front worst-case cost
  preflight. The budget does not cover online solver, optimizer-judge, or
  rubric-proposer stages.
- Blinded human A/B packets are available for independent adjudication. Human
  labels are not automatically treated as the primary outcome.

## Recommended sequence

1. Complete the current unfiltered experiment without changing its treatment
   midstream; treat it as a diagnostic baseline.
2. Audit existing rubric proposals for recurrence, semantic overlap, false
   positives, and temporal association with RH outcomes.
3. Implement shadow evolution and offline frozen-rubric rescoring.
4. Move formalizable process violations into deterministic enforcement.
5. Define a finite process-rule library and executable counterfactual tests.
6. Run a development experiment comparing static, unfiltered, gated, and
   shadow mechanisms.
7. Collect randomized forked continuations for training a conservative rubric
   controller.
8. Freeze the selected system and evaluate it once on untouched tasks with a
   prespecified high-confidence RH bound.

The core research principle is that model-generated critique is evidence to be
tested, not authority to change the reward. Stronger guarantees come from
restricting action spaces, collecting causal interventions, pessimistic
selection, deterministic enforcement, and untouched statistical certification—not
from increasingly elaborate proposer prompts.
